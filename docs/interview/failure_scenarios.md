# Failure scenarios

One table to answer "what happens when X breaks". Read a row left to right: what you would see, what the code does today, where that code lives, what production would add, and the one sentence to say out loud.

How to read it:
- Paths are under `feedback_ingest/` unless they start with `scripts/` or `tests/`.
- Everything in this table is built and on `main`, and the rows match that code.
- Terms like lease, fence, dead letter, replay, cursor and overlap window are defined in `docs/interview/glossary.md`.
- Two more words used below. **Tick**: one pass of the scheduler over all enabled pull sources, every `FI_PULL_INTERVAL_SECONDS` (default 300, that is 5 minutes). **429**: the HTTP reply that means "too many requests, slow down".
- Where a row quotes Enterpret, it quotes their public help center or engineering blog only. We do not know how their system works inside.

| **Source API down, or 429, while pulling** | `POST /v1/sources/{id}/sync` returns 502 with the result and `"error": "429 from https://…/search.json"`. The message holds the status and the URL, never the reply body. A WARNING log line says `pull stopped at the saved cursor: 429 from …`, with `source_id=`. The cursor does not move. After a scheduled tick fails, `/health` still answers 200 `ok`, and `failing_sources` counts the source. It is a count only: `/health` has no auth, and a source id is half of a webhook credential, so the id stays in the log line. | The HTTP adapter turns 429, 408, 5xx, network errors and the 10-second timeout into `TransientError`. Other 4xx replies, and any 3xx (we do not follow redirects), become `PermanentError`. The pull stops at the first error of either kind, keeps the pages already saved, and tries again next tick. The Discourse cursor only moves on the final page of a run, so the next run starts from the same bookmark, and the repeats are dropped by the unique key. A failing upstream does not change the health status code: only a dead worker or scheduler thread does. | `adapters/http/httpx_client.py`, `services/pull.py`, `services/scheduler.py`, `api/health.py`, `connectors/discourse_pull.py` | Honour the `Retry-After` header. Ours is a setting, so slowing down is a config change. | "We stop, keep what we already saved, and try again next tick from the same bookmark; the repeats that causes are dropped by the unique key." |
| **Slow, huge or redirecting upstream** | The sync result `error` reads `pull deadline exceeded`, or `response too large from https://…`, or `301 from https://…`. The cursor does not move. | One sync has a wall-clock budget, `FI_PULL_DEADLINE_SECONDS` (default 60). The puller checks it before each search page and each `posts.json` call, and stops with `TransientError("pull deadline exceeded")`. One upstream reply is capped at `FI_HTTP_MAX_BYTES` (default 2,000,000 bytes): the body is streamed and the read stops past the cap. Redirects are not followed, and proxy settings from the environment are ignored, so a public `base_url` cannot bounce us to an internal host. | `connectors/discourse_pull.py` (`_check_deadline`), `adapters/http/httpx_client.py`, `config.py` | Per-source budgets. A metric for sync duration and reply size. | "A sync has a time budget and a size cap, and it never follows a redirect, so one bad upstream cannot hang the scheduler or point us at an internal host." |
| **Busy forum: more than 10 search pages** | Every sync returns 502 with `pages: 10` and an error that says `window exceeds 10 pages; about 500 posts per day is the hard limit of Discourse search; lower window_days via PATCH`. The cursor stays at `start_after`, or at its old value. Each run re-reads the same pages, so they come back as duplicates. | Discourse search answers 400 for page 11, so the puller stops after page 10 (about 500 posts). It never reaches the final page, so the cursor never moves. The fix is a smaller window: `PATCH /v1/sources/{id}` with `{"config": {"window_days": "1"}}`. | **Two syncs of one source at once** | A manual sync gets 409 `source … is already syncing`. The scheduler logs INFO `skipped: a manual sync is running`. | `PullService` holds one lock per source and only tries it, never waits. A manual sync that finds it taken answers 409. The scheduler skips the source and does not count it as failing. The lock lives in one process, so two processes can still sync one source at once; the unique raw-event key absorbs the repeats. | `services/pull.py`, `services/scheduler.py`, `api/sync.py` | A lock in the database, such as a lease row per source, if several processes pull. | "One source syncs one run at a time per process; a second request gets a 409, and across processes the unique key still keeps it safe." |
| **DB down on push** | The sender gets 503 `{"detail": "storage unavailable"}`. An ERROR log line says `storage unavailable: POST /v1/sources/…/events` with a traceback. No raw row exists. | Every SQLAlchemy `OperationalError`, `InterfaceError` and `TimeoutError` becomes 503. That includes the source lookup, which runs first. SQLite waits up to 5 seconds for a lock (`busy_timeout`) before it gives up. We answer 202 only after the raw row is committed. | `api/errors.py`, `api/ingest.py`, `adapters/sqlalchemy/db.py` | Managed Postgres with failover. An alert on the 503 rate. A small spool in front of the database if a sender does not retry. | "We never say yes before the row is on disk, so the sender gets a 503 and retries, and nothing we accepted is lost." |
| **DB down on pull** | Scheduler: an ERROR line `scheduled sync failed` (with `source_id`) and the traceback for each source the outage hits; the tick moves on to the next source, or `scheduler tick failed` if listing the sources failed. Manual sync: 503 `{"detail": "storage unavailable"}`. | The pull service catches only source errors (`TransientError`, `PermanentError`). A storage error is ours, so it propagates. The endpoint's 503 handler answers it; any other unexpected error is a 500. The scheduler catches it per source (and per tick), so the thread lives on, and `/health` counts it in `failing_sources`. The cursor is saved only after that page's raw rows are committed, so it never points past unsaved data. The next tick tries again. | `services/pull.py`, `services/scheduler.py`, `api/errors.py` | An alert on repeated failed ticks. Count failed ticks on `/health`. | "The bookmark only moves after the rows are saved, so a failed tick just means we fetch the same page again next time." |
| **DB down while the worker polls** | An ERROR line `worker iteration failed` about once a second. After about 10 seconds the worker counts as unhealthy, and `/health` returns 503 `degraded`. If reads fail too, `/health` answers 503 `storage unavailable` at once, because it also reads the queue counts. | The claim fails. The loop logs it, sleeps for `FI_WORKER_POLL_SECONDS`, and tries again, forever. Rows wait on disk as `pending`. If an event was mid-process, its finish call fails and the log says `process crashed`. The row stays `processing` until its 30-second lease runs out, then it is claimed again. | `services/worker.py`, `api/health.py` | Back off on repeated loop errors. Alert on health. Track the age of the oldest pending row. | "The worker keeps retrying the claim, the work is still on disk, and health turns red so we notice." |
| **Worker crash mid-event** | After a restart the row shows `processing` with an old `lease_until`. Within 30 seconds it is claimed again and `attempts` goes up by one. If the old worker was only slow, you may see WARNING `lease lost; a newer claim owns this event`. A payload that crashes the whole process every time ends `dead` with `attempt limit exceeded; last error: …`. | A claim sets `lease_until = now + 30 s` and adds one to `attempts`. A `processing` row whose lease has passed can be claimed again. The record upsert is keyed on `(source_id, external_id)`, so running it twice gives the same row. The fence makes the late worker's finish do nothing. Before it runs the transform, the pipeline checks `attempts`: once it is above `FI_MAX_ATTEMPTS` (5), the event goes dead with `attempt limit exceeded`, so a payload that kills the process every time stops after its sixth claim. | `adapters/sqlalchemy/raw_event_queue.py` (`claim`, `_finish`), `adapters/sqlalchemy/feedback_store.py`, `services/pipeline.py` (`process`) | Lease heartbeats for long jobs. An alert on `attempt limit exceeded`, because it means something keeps killing the worker. | "The lease runs out, the row is picked up again, and the upsert makes doing it twice the same as doing it once." |
| **Worker thread dies** | `/health` returns 503 with `"status": "degraded", "worker_alive": false`. `pending` grows in `/admin/queue`. Webhooks still get 202. | The loop catches every `Exception`, so only something rarer, like a `BaseException`, can kill it. Nothing restarts the thread. Intake keeps working, because the webhook does not need the worker. Restart the process: pending rows drain, and rows that were in flight come back after the lease. | `services/worker.py`, `api/health.py` | Run the worker as its own process under a supervisor that restarts it when health fails. Alert on queue age. | "Health goes red and the queue grows, but intake keeps working; restart the process and the backlog drains from disk." |
| **Scheduler thread dies** | `/health` returns 503 with `"status": "degraded"`, `"scheduler_enabled": true` and `"scheduler_alive": false`. Pull cursors stop moving. | Health counts the scheduler as well as the worker: if the scheduler is turned on and its thread is gone, the status is `degraded`. With `FI_SCHEDULER_ENABLED=false` it is not counted. The scheduler loop catches errors per source and per tick, so only something rarer, like a `BaseException`, can kill it. Nothing restarts the thread. Manual sync still works. | `api/health.py`, `services/scheduler.py` | A supervisor that restarts the process when health fails. An alert on the age of each source's last good sync. | "Health goes red when the scheduler is gone, and manual sync still works until we restart it." |
| **Duplicate webhooks** | The second delivery gets 202 `{"raw_event_id": "<the stored row's id>", "duplicate": true}`. The log says `accepted (duplicate=True)`. If the stored copy is `dead`, a WARNING line also says `duplicate of a dead raw event; left dead, replay it`. | `raw_events` is unique on `(source_id, external_event_id)`. The event id is the item id plus its last-changed time (Intercom adds a short hash of the item), or a hash of the payload when it does not parse. The second copy is dropped, and we still answer 202 so the sender stops retrying. A re-send does not bring a dead event back; a replay does. If two copies ever got through, the record upsert still keeps one row per item. | `services/ingestion.py`, `adapters/sqlalchemy/raw_event_queue.py` (`enqueue`), `connectors/*.py` (`external_event_id`) | On Postgres, use `INSERT … ON CONFLICT DO NOTHING`. Today it is "read, then insert" in one write transaction, which is safe on SQLite because the write lock is taken first. | "Same item, same update time, same key: the second copy is dropped and we still answer 202." |
| **Out-of-order edits** | Nothing looks wrong. The older copy's event is `processed`, and the record keeps the newer text. | Each edit is a new raw event, because the key includes the update time. The upsert compares the "last changed" time (update time, or create time if there is none). Older loses (`skipped_older`). Equal or newer wins. A delete always sets `deleted_at`, even when it arrives late, and it is never undone. | `adapters/sqlalchemy/feedback_store.py` (`upsert`), `domain/models.py` (`version_at`) | Count `skipped_older` as a metric. Use the source's own version number where it has one. | "A record only moves forward in time: an older edit that arrives late loses the timestamp check." |
| **Intercom sends every change to a conversation** | One Brightwave conversation produces several raw events, one per update. `/v1/records` shows one record with the latest text and `state`. | Intercom pushes a full snapshot of the conversation on each `conversation.*` topic. Enterpret's help center describes ingesting resolved conversations only for support tools. We keep open ones too, so a record can change after it first appears. | `connectors/intercom.py`, `adapters/sqlalchemy/feedback_store.py` | A per-source filter on `state` for tenants who want resolved conversations only. | "We keep every snapshot and the newest one wins, so an open conversation is visible early and updates in place when it closes." |
| **Transformer bug shipped (fix + replay)** | Records with wrong fields, all with the same `connector_version`. Or a wave of `dead` events with the same error. | Raw payloads are kept as received. Fix the connector, bump its `version`, restart, and replay. One event: `POST /admin/raw-events/{id}/replay`. It works on `dead`, `failed` and `processed` rows, and on a `processing` row whose lease has expired; it answers 409 only while a worker holds a live lease. Many events: `POST /admin/raw-events/replay?source_id=…&status=dead` (or `failed`, or `processed`), up to `limit` rows per call (1 to 500, default 500), newest first, only the caller's tenant. It returns `{"replayed": n}`. Replay runs the same upsert, and an equal timestamp counts as "newer or equal", so the fixed output overwrites the row. Replay order does not matter: older versions are skipped and deletes stay. | `api/admin.py`, `adapters/sqlalchemy/raw_event_queue.py` (`replay`), `connectors/*.py` (`version`) | Bulk replay by connector version and time window, run as a background job. | **Poison payload** | The event is `dead` after one attempt. `error` reads like `comments: Field required`: the field path and the message, no customer text. | **Oversized or badly shaped body** | 413 `body too large` for a body over 1 MiB. 400 `body must be a JSON object` for a body that is not a JSON object, or is nested too deep to store. | A middleware on every route counts the body: the `Content-Length` header, or the bytes as they stream in. | **Webhook sent to a pull source** | 409 `source does not accept webhooks`. | Webhooks are push-only. | **Slow transform blocking** | `pending` grows. `/health` returns 503 `degraded` if one batch takes longer than about 10 seconds, even though the thread is alive. ## The three sentences that answer most of these

1. **Durable before ack.** We save the raw payload to disk before we say 202, so a crash, a restart or a database outage can delay work but cannot lose anything we accepted. If we cannot save it, we answer 503 and the sender retries.
2. **Idempotent upsert keyed on source + external id.** Every record is keyed on `(source_id, external_id)`, and every raw event on `(source_id, external_event_id)`. So a duplicate webhook, an overlapping poll or a second run after a crash all end in the same single row.
3. **Everything after acceptance is a retry or a replay.** Flaky failures retry with backoff. Permanent ones go to the dead list. After a fix, a replay runs the stored raw payload through the transform again.
